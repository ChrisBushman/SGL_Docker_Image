０．マニュアルバグ情報======= ！！！！ 重要  ！！！！ ======================

 （１）Ver1.00以前のバックアップライブラリユーザーズマニュアルにて、
     ライブラリの作業領域の大きさが「8192バイト必要です」とありますが、これは
     120バイト少ない値でした。実際には、8312バイト必要です。
     作業領域の大きさを下記の様に変更してください。
        誤)   Uint32  BackUpRamWork[2048];
                                     ↓
        正)   Uint32  BackUpRamWork[2078];

     本作業領域には、パワーメモリーの管理情報等を格納します。
     バックアップライブラリの使用中に、本作業領域が破壊される事のないように
     注意して下さい。
     （作業領域が破壊された場合、BUP_Init()を実行して再度初期化が必要です。）
     ========================================================================

 （２）SGLチュートリアルマニュアルに記載の BUPライブラリを使用するサンプル
     プログラムには、次の様なバグが有りました。
     ・日付の計算ミス
     ・ライブラリワーク領域の確保に問題があり、変数スコープが足りない。
     以上の不具合は、現在提供中の SGLに付属のサンプルでは修正されています
     ので、そちらを参考にして下さい。

１．  ライブラリファイル（sega_bup.lib）の提供と注意事項
  これまでは、ライブラリ関数の呼び出しはマクロ形式によるものであり、ヘッ
ダファイル（sega_bup.h）だけが提供されていました。
  バージョン1.10 以降からは、ライブラリファイル（sega_bup.lib）も提供され、
ライブラリ関数の呼び出しは通常の関数形式となります。
  従って、Ver1.10から BUPライブラリを使用するには、sega_bup.libをリンクする
必要があります。
  Ver1.10はシリアルインターフェース部分に関してバグがありました。
  今後発売するソフトに関しては、FDD使用、未使用に関わらずVer1.21以降のバック
  アップライブラリを使用してください。

  使用上の注意事項を以下に示します。

（１）  Ver1.21以前のバックアップライブラリではFDDなどのシリアルインター
     フェースに接続するバックアップ機器の初期化がうまくできません。
     今後のアプリケーションは、バックアップライブラリ Ver1.24 以降を FDDの
     使用、未使用に関わらず使用してください。

（２） バックアップライブラリVer1.00 までと違い、ライブラリをリンクして
     使用します。
     
     SHCではsega_bup.libを
     GCCではsega_bup.aをリンクして使用します。

     それぞれのライブラリの大きさは、次のようになっています。
     sega_bup.lib  2307バイト
     sega_bup.a    3620バイト

     これらを使用するためには、これまで通りのライブラリ展開領域16KBのほかに、
     ライブラリのリンク分のメモリ領域が必要になります。
     サターンFDD に対応する場合は、BUPライブラリ(BOOT-ROMから展開する分と、
     上記ライブラリファイルの両方)を WORKRAM-HIGH に配置する必要があります。

     ※注意==================================================================
     また、ライブラリの作業領域の大きさは、バックアップライブラリユーザーズ
     マニュアルP.43で「8192バイト必要です」と書いてありますが、8312バイト
     必要になります。今後発売するソフトに関しましては、作業領域の大きさに
     注意してください。
     ========================================================================
     
（３）  リセットボタンと割り込みの禁止処理について（注意：Ver.1.24から変更あり）

  Ver.1.10からVer.1.23まではリセット無効処理と割り込み禁止処理はバックアップ
  ライブラリ内部で実行していました。（PER_SMPC_RES_DIS/ENA, set_imask）
  
  Ver.1.24からはリセット無効処理をライブラリ外部で実行するVer.1.10以前の形式に
  戻しました。PER_SMPC_RES_DIS/ENAを使用し、各自リセット有効無効処理を実行して
  ください。また、割り込み禁止処理に関しては内部で実行しています。
  
  
（４） BUPライブラリのメモリ制限について
  Ver.1.20以降を使用してシリアルインターフェース（FDドライブなど）を使用する
ときは、BUPライブラリをWORK RAM HIGHに置いてください。
  シリアルインターフェースを使用しない本体またはパワーメモリのみバックアップと
して使用するときはWORKRAM LOWにBUPライブラリを置いてもかまいません。

（５） Ver1.20以降使用の場合のペリフェラルの扱いについて
    バックアップライブラリVer1.20以降を使用する場合、96.1.26以前の SMPC I/F
    ライブラリ(sega_per.lib  sega_per.a)では SMPC割り込みで不具合が発生する
    可能性があります。
    万一、バックアップライブラリVer1.20以降の使用により、ペリフェラルのデータ
    取得に異常が発生した際には、以下の方法にしたがって、SMPCのSCU割り込みの
    優先順位の変更を行ってください。

    ●SCU割り込みの優先順位 変更具体例

        0x0070ff7f,  0x0070ff7e,  0x0070ff7c,  0x0070ff78,

３．ＦＡＱ集

Q1:
フロッピードライブの接続状態チェックにて、
次の区別は可能でしょうか？
 (a):ドライブが未接続
 (b):ドライブ接続かつ、ディスク未挿入
 (c):ドライブ接続かつ、未初期化ディスク挿入
 (d):ドライブ接続かつ、初期化済みディスク挿入(正常)

A1:
現在のバックアップライブラリでは、次のようにして接続状態を判別可能です。

・初期化時にBUP_Initで ドライブ接続およびディスク挿入のチェック
	Bup_Initの3番目の引数BupConfig conf配列を使用します。
	  conf[2].unit_id が 3 でかつ conf[2].partition が 2
	  → ドライブ接続 かつ ディスク挿入 → 次の処理へ。
	  conf[2].unit_id が 0 でかつ conf[2].partition が 2
	  → ドライブ接続 かつ ディスク未挿入 (b)
	  conf[2].unit_id が 0 でかつ conf[2].partition が 0
	  → ドライブ未接続 (a)
・BUP_SelPart パーティションを選択(サターンFD は２パーティション構成)
・BUP_Statでフォーマット&空き容量チェック → (c)(d) のチェック
   ・BUP_NON        未接続又は未挿入 (a) または (b)
   ・BUP_UNFORMAT   未初期化ディスク (c)
   ・0                     正常      (d) → その他の処理を実行可能


(a)は Bup_Initの3番目の引数BupConfig conf[3]の conf[2].unit_id = 3;
が返ってきたら、FDドライブが接続されています。0ならドライブ未接続です。

(b)は、BUP_StatでBUP_NONが返ってしまいます。これは、
(a)の場合も同じですから、途中でFDDが抜かれたら判断できません。

(c)はBUP_StatでBUP_UNFORMATを検出してください。

(d)は正常なので普通の使い方です。

よって
・初期化時やディスクの交換が発生しうる場合 → BUP_Initで接続 & 挿入チェック
・その他のチェックの場合 → BUP_Statを使います。
または、
・初期化時に BUP_Initで接続チェック
・その他のチェックの場合 → BUP_Stat
   → (BUP_NON の場合)BUP_Init で再度接続チェック
      (その他)適切な処理を行う
という手順でチェックすれば問題ありません。


Q2:
ライブラリ作業領域は、いつの時点まで保持する必要
があるのでしょうか？
例えば次のような使用方法では問題はありませんでしょうか？
BupConfig *	BackUpInit(void)
{
    Uint32  BackUpRamWork[2078];  /* スタックに確保 */
    BupConfig cntb[3];                /* スタックに確保 */
    /* bupライブラリ初期化 */
    BUP_Init((volatile Uint32 *)BUP_START_ADDR,BackUpRamWork,cntb);
    return (cntb);
}

void	main(void)
{
    BupConfig *cntb;
        :
    BackUpInit();  /* バックアップライブラリ初期化処理 */
        :
    /* その他(セーブ・ロード)等の処理を行う */
        :
}

A2:
このような使用の仕方はできません。BUP_Initの時に要求するワーク領域は
バックアップRAMを使用している間、その領域を確保し続ける必要が
あります。
ワークにはバックアップライブラリ内部のグローバル変数とパワーメモリ
のアクセステーブルが入っています。もしこの領域を開放したり、一時的に
他の目的に使用した場合は、もう一度バックアップライブラリを使用する際に、
BUP_Initからやり直す必要があります。


Q3：セーブデータのサイズ指定について
	データ構造体「BupDir」に「blocksize」データのサイズ（ブロック単位）
	というメンバーがあるようですが、使用方法が分かりません．
	（どのサンプルプログラムでも使用していないようです．）
	「datasize」には、セーブデータのサイズをバイト単位で設定するよう
	ですが、「blocksize」には何も設定しなくて良いのでしょうか？
	
A3：
	BUP_Write関数のマニュアルに書いてある通り「blocksize」は何も
	入力する必要はありません。
	ディレクトリ情報を取得した場合は、正しい値が取得されます。
	ただし通常は使用する必要の無いものです。(下記参照)


Q4：「ブロック」の定義と空き容量チェックについて。
	STN-9 によると、
	１ブロック ＝( ( [データバイト数] + 32 ) / 64 ) の切り上げ
	となっていますが、この定義式は全てのメディアに共通ですか？
	また、空き容量のチェックに この計算式で使用したブロック数は
	使用できますか？

A4：
	式そのものは全てのメディアで共通です。
	ただしこの計算式で算出した空き容量は、実際には使用できません。
	残り容量のチェックは、データのバイトサイズで行なって下さい。
	上記の式はマルチプレーヤーやＦＤＤオペレーター内で
	使用している「表示上」のブロック計算式です。
	これは本体バックアップＲＡＭの計算式をすべてのメディアに用いる
	ことによって、違うメディアにデータをコピーする場合に、ユーザー
	にわかりやすくしたものです。
	一方ライブラリ使用時における blocksize はメディアに固有な値で、
	なんら関係ありません。
	ライブラリ内部で使用する「ｂｌｏｃｋ」の定義は、各メディア毎に
	異なります。
	(説明の都合上、一般ユーザ向け表示上のブロックはカタカナ表記、
	メディア固有のブロックは英語表記(block)で記述します)

	各メディアのｂｌｏｃｋサイズは次のようになっています。
	
	本体                １ｂｌｏｃｋ ＝     ６４バイト ＝   １ブロック
	パワーメモリ(1)     １ｂｌｏｃｋ ＝   ５１２バイト ＝   ８ブロック
	パワーメモリ(2)     １ｂｌｏｃｋ ＝   ２５６バイト ＝   ４ブロック
	ＦＤ                １ｂｌｏｃｋ ＝ ４０９６バイト ＝ ６４ブロック

	表示上のブロック    １ブロック   ＝     ６４バイト

	例えば本体に６４バイト（１ｂｌｏｃｋ）の記録があるとします。
	ここで言う「記録」とは、データ＋ヘッダ＋メモリ管理情報 の意味です。
	この記録をＦＤにコピーする場合、ＦＤの１ｂｌｏｃｋは４０９６バイト単位
	の為、４０９６バイト(６４ブロック分)を消費します。
	つまり表示上は１ブロックの記録が、実際は６４ブロック分のメモリを確保
	した事になります。	(1～63ブロック という空き容量は FDDでは有り得ません)

	異なるメディア間で記録をコピーする際の空き容量(ブロック)を比較する場合、
	コピー先に記録のブロック数以上の空きブロックがあれば、コピーできることが
	保証されます。
	具体的にはＦＤＤ側に表示上６４ブロック以上残っていれば、他にメディア上の
	１～６４ブロックの容量の記録がコピーできる事になります。

	いずれにせよ、ライブラリの使用時にユーザ側で ｂｌｏｃｋ数を考慮する
	必要性はありません。プログラム的な管理はバイト数で行う方が確実ですし、
	ユーザに通知する容量(ブロック)は バイト数を元に計算する必要があります。
	プログラム中での容量チェックには、BUP_Stat関数にて取得した ステータス
	情報中の、datanum(書き込み可能件数)で確認するようにしてください。


Q5：「使用量」の算出式について
	上記の定義式中にて加算している「３２」とは、ディレクトリ情報
	であると解釈していたのですが、ライブラリマニュアルによると、
	構造体「BupDir」のサイズは３４バイトあります．
	計算が合わない理由を教えて下さい．

A5：
	ご指摘の通りBUPDir構造体は３４バイトあります。ファイル名とコメ
	ントはそれぞれ１２バイトと１１バイトありますが、それぞれの最後
	の１バイト分はNUL文字になっています。
	データをセーブするときにはNUL文字を取った形でセーブしますから
	２バイト少ない３２バイトになる訳です。


Q6：正常にセーブ出来ません。
	初期化チェックと容量チェックを行った後でセーブを行っているのですが、
	なぜか正常にセーブ出来ません。考えられる原因を教えて下さい。
A6：
	WORKRAM上のセーブデータを割込み内で書き換えていませんか？
	ライブラリはセーブの後にベリファイチェックを行いますので、
	ライト後にデータが書き換わるとベリファイエラーとなり、自動的に
	消去されます。(実話です。)
	なお、BUPライブラリVer1.25以降では、処理中に割込みマスクを行いますので、
	同様の現象は発生しなくなるはずです。


Q7：残り容量のチェックにおいて BUP_Stat関数にて取得した ステータス情報中の
	databum(書き込み可能件数)と、freesize(空きバイト数)の計算が合わない
    のですが？
    具体的には、freesize ＝ 260 の時、64バイトのデータが４つセーブ出来ると
    思うのですが、BUP_Stat関数を実行した結果、datanum には 2 が返ります。
A7：
	バックアップライブラリの仕様です。
	freesize バイトのデータを「１つ」セーブ可能なのは保証できますが、
	(freesize / N)バイトのデータを「N個」セーブする事は保証できません。
	複数のデータをセーブしたい場合は、必ず datanumを参照してください。

Q8：異なるデータサイズで複数セーブを行う場合の容量チェックの方法は？
A8：
	容量の異なる記録をセーブしたい場合、容量チェックを 正確に1度に行う
	方法はありません。
	１つの記録について容量チェック→セーブする→次の記録の容量チェック
	→セーブする→ ・・・
	の繰り返しでチェックする以外に方法はありません。
